# Evolve — Maintainer Contract

## Purpose

Evolve helps a human and agent structure one substantial Project as a
deliberately progressive sequence of coherent advances. It creates and gates
an Evolution Map, waits for the human to select exactly one Evolution, then
collaboratively develops and gates that Evolution's complete high-level
specification. Evolve owns progressive strategy, Evolution meaning, native
gate consequence, route, and stopping; supporting skills return bounded
evidence or reaction without taking that ownership.

## Invocation, entry, and exclusions

Evolve is model-invoked because an active Formalization owner may recommend
progressive Evolution design and the human must be able to select it in
ordinary language. Host discovery never satisfies behavioral entry. Entry
requires an explicit human choice of Evolve, normally after Formalize explains
why at least two coherent Project advances could benefit from sequential
specification and learning. A direct human request to use Evolve is the same
choice.

Preserve entry provenance on every return:

- `human-selected` means the human chose Evolve and the route began;
- `declined-suggestion` means a caller suggested Evolve and the human
  declined; and
- `not-selected` means the suggestion or route was discussed but no choice was
  made.

The latter two are pre-entry stops. They create no Map and make no approval,
comprehension, or route claim. A later explicit choice is a new entry.

The entry brief supplies:

- one accepted Project Brief and Requirements, with source, revision,
  provenance, and limits;
- current system and domain model, relevant References, evidence, known
  dependencies, uncertainty, change pressure, and human preference;
- caller, earliest causal owner, route and gate context, authority,
  acceptance boundary, and stop; and
- the exact effect or persistence boundary for this run.

Missing accepted context, authority, source, or a Project boundary that cannot
be judged without guessing is not permission to invent a Map. A Project that
combines, omits, or misstates substantial outcomes returns the concrete
conflict to Requirements Discovery. A Project with only one useful coherent
advancement returns to Formalize for direct Issues.

Evolve excludes mechanical Project or Evolution classification, exhaustive
Requirement traceability, feature or release taxonomy, detailed behavior or
interface definition, Issue definition, Implementation Plans, implementation,
mutation, authority grants, commits, publication, deployment, automatic
Evolution selection, automatic lifecycle progression, and adjacent cleanup.
It does not preserve implementation chronology, create a Decision record, turn
a learning-only probe into an Evolution, mutate a Project Brief, or use
approval as a forward choice or mutation authority.

## Behavioral contract

Evolve owns this bounded sequence:

1. confirm entry provenance and bind one Project's accepted context;
2. collaboratively propose the smallest useful Map with at least two coherent
   working advances and concise future detail;
3. resolve only bounded mapping or high-level specification questions through
   direct supporting calls while retaining Map and Evolution ownership;
4. present and gate the Map, stop after Map Approval, and wait for one explicit
   human Evolution selection;
5. validate that selection against exactly one existing stable Map ID, then
   create and collaboratively complete only that Evolution's high-level
   specification;
6. present and gate Evolution Definition Approval, stop, and recommend Issue
   definition without starting it; this section completes only after the exact
   Definition revision returns as approved, a typed causal return, a typed
   native stop, or a typed native command/transport blocker, with no Issue or
   Delivery activity begun; and
7. gate an integrated result when selected, classify delivered learning,
   revise and re-gate only affected progression, or return the route to its
   causal owner, then return one result and stop; this section completes only
   after the exact Result Gate claim closes with proved coverage or returns its
   typed partial, causal, stopped, or native blocked state, with every Map
   revision visibly pending its own gate.

## Invariants

1. Evolve begins only after an explicit human selection of the Evolve route;
   a loaded package or unaccepted suggestion is not entry. Declined and
   not-selected suggestions return with honest pre-entry provenance.
2. Every entered run binds one Project boundary, accepted Requirements,
   current evidence, human preference or approach, caller, authority,
   acceptance boundary, and visible limits, or returns a typed blocker or
   causal return.
3. Project and Evolution boundaries are collaborative judgments derived from
   Requirements, territory, system, complexity, uncertainty, dependencies,
   and preferred solution; feature, subsystem, technical-layer, migration,
   milestone, release, audience, and Plan labels never classify them alone.
4. A Map contains at least two coherent integrated working advances. Each is
   real enough to exercise, review, prove, and learn from in its Project.
5. Stable descriptive Evolution identity is independent from `E1`, `E2`, or
   another sequence position. Reordering changes position or filename, not a
   stable accepted ID.
6. Before creating a selected Evolution file, the human's selection resolves
   to exactly one existing current Map entry by stable ID; zero, duplicate, or
   sequence-position-only matches create no file and return the exact
   `blocked_state`.
7. Each Map entry has stable ID, sequence position, tangible advancement,
   deliberate limitations, position value, and an optional learning target.
8. The Map explains collective Project Requirements coverage and exposes
   consequential omissions, dependencies, change pressure, and uncertainty;
   it uses the exact `Governing Context`, `Progressive Strategy`, `Evolution
   Sequence`, optional `Cross-Evolution Dependencies and Uncertainty`, and
   `Current Recommendation` bodies and never becomes an exhaustive
   Requirement ledger or future Issue/Plan.
9. A learning target names a consequential uncertainty and a named later Map
   judgment. Learning-only work is not an Evolution without a tangible
   integrated advance.
10. When several decompositions are serious, Evolve compares consequences and
    recommends one. When only one useful advance remains it returns
    `one-advance` with a typed causal return to Formalize and recommends direct
    Issues; it never manufactures entries.
11. If every sequence is artificial because the Project boundary is wrong,
    Evolve returns the concrete conflict to Requirements Discovery rather than
    hiding it in the Map.
12. The complete Map is written at `evolutions/map.md` before its native gate;
    no empty placeholder is created. The selected Evolution file is created
    only after one explicit stable-ID selection at
    `evolutions/eN-<name>.md`.
13. Record lifecycle rules are loaded directly from `foundations.md` when a
    Map or Evolution is created, moved, materially revised, superseded, or
    closed. Map and Evolution bodies are authored and validated against
    `formalization.md`. Neither reference chooses a route, grants authority,
    calls another reference, or stops Evolve.
14. A visual or structured surface uses the lowest fidelity that makes the
    progression judgeable. Make Tangible owns construction, verification,
    reaction, and artifact lifetime; a reaction is not a Map decision or gate.
15. Research is called only for one factual sequencing premise that can
    change the Map or selected high-level form. Interview is called only for
    one human-owned working-form judgment. Orient is called only after the
    human accepts a bounded suggestion to understand a settled Project,
    system, or Map model. Design Solution is called only for one consequential
    solution shape after a complete preflight. Research
    `needs-human-judgment` becomes top-level `causal-return` with the exact
    human or causal owner, `boundary_id`, missing qualification and changed
    meaning, Research evidence and limits, and the owner's revisit condition.
16. Design Solution preflight contains a stable boundary, active caller and
    earliest causal owner, accepted Requirements/specifications with source,
    revision, provenance, and limits, current evidence with provenance,
    revision/freshness, and limits, one exact choice with applicability and
    wrong/defer consequence, territory/actors/scenarios/boundaries, hard
    Requirements/safety/invariants/compatibility duties, evidence standard and
    authority, feasible/current/caller-accepted/provisional alternatives, and
    caller-retained route/gates/authority/acceptance/stop. Missing fields
    return a typed causal return and never become a guess or a Design Solution
    call.
17. Plannotator is called directly only for Evolve-owned native Record Gates
    (Map or Evolution Definition) or an applicable Result Gate (integrated
    Evolution Acceptance). A missing artifact is constructed and verified by
    its owner before a native gate.
18. Every direct call carries its exact bounded trigger and return shape. The
    callee retains its procedure and evidence/reaction ownership; Evolve
    retains strategy, synthesis, records, gate consequence, route, authority,
    acceptance, and stopping. No callee re-enters Evolve for the same boundary.
19. Map Approval accepts only the exact current progressive strategy. It
    selects no Evolution, begins no specification or Issue work, and grants no
    planning, mutation, external, or forward authority.
20. Evolution Selection is a separate ordinary-language human choice naming
    exactly one stable Evolution. Approval, recommendation, sequence position,
    “continue,” or silence never selects one.
21. Evolution Definition Approval accepts only the selected Evolution's
    complete high-level specification. It begins no Issue definition, Plan,
    Delivery, implementation, later Evolution, or adjacent cleanup.
22. A selected Evolution contains `Governing Context and Accepted Truth`,
    `Tangible Advancement`, `Included High-Level Behavior`, `Integration with
    Existing Project Work`, honest `Deliberate Limitations`, an applicable
    `Learning Target`, `Required Proof`, and `Current Recommendation`.
    `Accepted Result` appears only after Evolution Acceptance. It remains above
    detailed flows, interfaces, edge cases, failure cases, dependencies,
    files, commands, checks, and mutation authority.
23. Later accepted Evolutions may create pressure on the current form. Evolve
    states that pressure as accepted truth, a limitation, or a learning target
    and never prescribes speculative future implementation.
24. Working-form proof and learning-target evidence remain separate. Delivered
    learning changes the Map only when it changes future number, order,
    boundary, meaning, or progression; other clarification may update locally.
25. Changed needs, constraints, or Project boundaries return to Requirements
    Discovery. Changed solution commitments or Evolution meaning return to the
    affected causal owner. Only progression learning belongs in a Map revision.
26. Material Map revision foregrounds the semantic diff, leaves the replacement
    Map pending, emits no recommendation or selection until that revision is
    approved, and repeats Map Approval for affected progression only. An
    Evolution that splits, merges, or changes identity is superseded and
    replaced with new stable IDs.
27. A Result Gate preflight names the actual working result, proved coverage,
    unproved claims, decisive evidence and checks with scope, limitations,
    learning and unresolved points, exact acceptance claim, and excluded
    adjacent actions. Partial results preserve unproved claims and never
    receive a full-result implication.
28. Result Gate approval closes only its exact named acceptance claim and
    proved coverage. Approval feedback that preserves meaning does not trigger
    a re-gate; meaning-changing feedback revises the causal owner and repeats
    only the affected gate. Denial, annotation/plaintext, dismissal, and
    closure never become approval. At Map and Definition Record Gates, native
    `closed` maps to `stopped` with `stop_reason.kind=native-closure`, while
    `dismissed` maps to `native-dismissal`. A rejected partial result preserves
    its proved and unproved state as `stopped`; native command or transport
    failure is the native gate `blocked` state.
29. If no multiple meaningful Evolutions remain, Evolve never mutates the
    Project Brief. It returns a typed causal return to Formalize for direct
    Issues, or Requirements Discovery when Project truth changed. It removes
    `evolutions/map.md` only after Foundations verifies that no current record
    or named consumer references it; otherwise it preserves the Map and names
    the cleanup limitation.
30. Map or Evolution acceptance keeps the accepted record and links decisive
    evidence and causal learning without copying a specification, acceptance
    transcript, or implementation chronology.
31. Every completion returns decisive evidence, provenance, limits, unresolved
    judgment, exact native decision when used, and the next human choice or
    causal owner. Approval, acceptance, or a supporting result never
    authorizes planning, mutation, commit, publication, deployment, or another
    Evolution.
32. Evolve stops after each Map Approval, required human selection, Evolution
    Definition Approval, Result Gate, causal return, blocked/stopped result,
    or learning revision. It never advances by momentum.

## Outcomes and observable return

Evolve exposes exactly these top-level outcomes:

- `map-proposed` — an unapproved Map is complete enough for human reaction;
- `map-revised` — a material Map change leaves the replacement Map gate
  pending; no recommendation or selection is emitted until it is accepted;
- `one-advance` — only one useful advance remains and the route returns to
  Formalize for direct Issues;
- `map-approved` — the exact Map passed Map Approval, no Evolution was
  selected, and one candidate is recommended for human choice;
- `selection-required` — the accepted Map awaits one explicit human Evolution
  selection;
- `evolution-selected` — one Evolution was explicitly selected and its
  high-level specification remains incomplete or under discussion;
- `evolution-specified` — the selected Evolution's complete high-level
  specification is ready for Definition Approval;
- `definition-approved` — the selected Evolution's exact high-level
  specification passed Definition Approval and Issue definition is only a
  recommendation;
- `causal-return` — changed Project truth, Requirements, solution meaning,
  missing Design Solution preflight, or other learning belongs to an earlier
  owner;
- `blocked` — a missing/invalid local boundary or dependency prevents an
  honest continuation, or a selected native gate failed at command or
  transport. Native denial, feedback, dismissal, and closure are not
  `blocked`; and
- `stopped` — the human stopped, a pre-entry route was declined or not
  selected, a native denial/feedback/dismissal/closure ended the bounded
  interaction, or a dependency stopped. The exact state remains in
  `stop_reason`.

The semantic return is:

```text
Evolve Result {
  outcome,
  entry: human-selected | declined-suggestion | not-selected,
  project_and_governing_context,
  map_state {
    path,
    stable_ids_and_sequence_positions,
    current_strategy,
    limitations_and_dependencies,
    learning_targets,
    gate_state,
    accepted_reference?
  }?,
  selected_evolution {
    stable_id,
    sequence_position,
    path,
    high_level_specification,
    gate_state
  }?,
  native_gate {
    interaction_kind: record-gate | result-gate,
    exact_target_and_revision,
    decision: approved | approved-with-feedback | denied | annotated |
              plaintext-feedback | dismissed | closed | command-failure |
              transport-failure,
    feedback_or_annotations?,
    declared_consequence,
    native_reference,
    fidelity_or_transport_limits,
    regate_required
  }?,
  result_gate_preflight_or_partial_state? {
    actual_working_result,
    proved_coverage_and_evidence,
    unproved_claims,
    checks_and_their_scope,
    known_limitations,
    learning_and_unresolved_points,
    exact_acceptance_claim,
    excluded_adjacent_actions
  },
  evidence_and_provenance,
  working_form_proof?,
  learning_evidence_and_causal_owner?,
  human_choice_or_missing_boundary?,
  causal_return? {                 # required for outcome=causal-return or one-advance
    owner,
    reason,
    boundary?,
    changed_meaning,
    exact_dependency_or_route_result?,
    evidence_and_limits,
    revisit_condition
  },
  blocked_state? {                  # required only for outcome=blocked
    kind: missing-context | invalid-selection-target | missing-preflight |
          dependency-blocked | native-command-failure | native-transport-failure,
    exact_boundary_or_target,
    dependency_or_failure_result?,
    partial_state?,
    repair_or_setup_recommendation
  },
  stop_reason? {                    # required only for outcome=stopped
    kind: human-stop | declined-suggestion | not-selected |
          selection-not-made | native-denial | native-feedback |
          native-dismissal | native-closure | dependency-stopped |
          result-not-accepted,
    exact_native_decision_or_partial_state?,
    revisit_condition?
  },
  recommendation_or_revisit_condition?,
  limitations_and_unresolved_points,
  caller_retained_route_gate_authority_acceptance_and_stop
}
```

`map-proposed` and `evolution-selected` are working states, not approvals.
`map-revised` identifies the affected gate still required and emits no
recommendation or selection until that gate is accepted. `map-approved`
contains no selected Evolution; `selection-required` contains no inferred
choice. `one-advance` carries its Formalize causal return. A causal return,
blocked result, and stopped result require their corresponding typed payload.
Native approval with non-meaning-changing feedback preserves feedback without
re-gating; meaning-changing feedback alone re-gates. Native denial,
annotation/plaintext, dismissal, closure, and command/transport failure remain
distinct. No result includes implementation authority or an adjacent route
transition.

Every result identifies the exact current record revision and native target or
reference when applicable, all material evidence and limits, stable IDs and
gate state, remaining human judgment, causal owner, and recommendation or
revisit condition. The caller decides what to revise or accept; Evolve stops.

## Effects, authority, persistence, and lifetime

Evolve may inspect current Project source, system evidence, References, and
accepted records; revise the working Map and selected Evolution inside the
human-selected Evolve route; create or remove their owner-shaped files; and
invoke bounded read-only, conversational, tangible, design, orientation, or
native gate interactions. A native Plannotator session may read or present its
exact target, but its approval remains only the declared gate judgment.

Creating or revising a Map or selected Evolution is the only durable product of
this package. Record paths, IDs, gate projections, disposition, supersession,
and cleanup follow Foundations and Formalization. A Map or Evolution remains
only while a named future owner, gate, or causal consumer needs its governing
truth, accepted basis, limits, or learning. Removing a Map on a direct-Issue
return is allowed only after the reference check in invariant 29.

Evolve does not mutate a Project Brief, Requirements, product code, or data;
execute a Plan; define Issues; create Plans; commit, push, publish, or deploy;
install or repair Plannotator; change external state; or authorize any effect.
Supporting artifacts, comparison surfaces, raw reactions, result transport,
and implementation chronology are transient unless a named future consumer
needs exact native evidence. Approval and acceptance do not grant authority or
start adjacent work.

## Package-specific conformance cases

1. A direct explicit human choice of Evolve enters with one accepted Project,
   Requirements, current context, authority boundary, and visible limits; a
   loaded or merely suggested route does not begin.
2. A declined suggestion returns `stopped` with
   `entry=declined-suggestion`, `stop_reason.kind=declined-suggestion`, no Map,
   and no approval claim. A discussed but unselected route returns the same
   honest pre-entry state with `entry=not-selected`.
3. A Project boundary that combines, omits, or misstates substantial outcomes
   returns a typed causal return to Requirements Discovery; Evolve does not
   hide it in a convenient Map or mutate the Project Brief.
4. Two or more category-neutral coherent advances form the smallest useful
   Map; feature, layer, migration, release, audience, or Plan labels alone do
   not qualify one.
5. A Map entry carries stable ID, sequence position, tangible advancement,
   deliberate limitations, position value, and only a consequential optional
   learning target; an exhaustive Requirement ledger is not created.
6. A learning-only probe without a tangible integrated advance is returned as
   evidence, not mislabeled as an Evolution.
7. A one-advance result is `one-advance` with a typed Formalize causal return
   for direct Issues and no manufactured second entry.
8. Several serious decompositions are compared by consequences and one is
   recommended; uncertainty and shared dependencies remain visible.
9. Research, Interview, Orient, Make Tangible, and Design Solution are called
   only at their bounded triggers, and each return preserves Evolve's strategy,
   synthesis, and stopping ownership. A missing Design Solution preflight field
   returns to the causal owner instead of becoming a guess.
10. Orient starts only after human acceptance of the bounded suggestion; a
    declined suggestion yields no comprehension claim or Map change.
11. A native Map Record Gate presents the complete stable Map and declared
    consequence. Approval without feedback and approval with non-meaning
    feedback accept only that Map and do not re-gate. Meaning-changing feedback
    revises only the Map and repeats its gate; the revised Map remains pending
    and emits no recommendation or selection. Native `closed` or empty closure
    is `stopped` with `stop_reason.kind=native-closure`.
12. Native denial preserves exact decision, feedback, reference or
    `unavailable`, and limits as `stopped`; it is not command failure. Native
    annotation or plaintext feedback is preserved as reaction and re-gates
    only when meaning changes. Dismissal maps to `native-dismissal`; native
    `closed` or empty closure maps to `native-closure` with no judgment;
    command or transport failure alone is native `blocked`.
13. Map Approval selects no Evolution. A human explicitly selects exactly one
    stable Evolution in ordinary language; approval, recommendation, position,
    “continue,” or silence never infers selection.
14. Before writing `evolutions/eN-<name>.md`, the selected stable ID resolves to
    exactly one existing current Map entry. Zero, duplicate, or
    sequence-position-only matches create no file and return
    `blocked_state.kind=invalid-selection-target`.
15. The selected Evolution file contains the complete high-level sections,
    honest limitations, applicable learning target, integration, and required
    proof without Issue or Plan detail. `Accepted Result` appears only after
    Evolution Acceptance.
16. A native Evolution Definition Record Gate applies the same complete
    decision mapping as Map Gate, including `closed` to
    `stop_reason.kind=native-closure`, accepts only the exact high-level
    specification, and stops before Issue definition or Delivery.
17. Result Gate preflight includes actual result, proved evidence/check scope,
    limits, learning/unresolved points, exact acceptance claim, and excluded
    adjacent actions. Partial/unproved coverage remains explicit; approval
    closes only named proved coverage, a refused partial result stops with its
    exact state, and meaning-changing feedback alone repeats the affected gate.
18. Delivered working-form proof is separate from learning-target evidence;
    accepted learning changes the Map only when future number, order, boundary,
    meaning, or progression changes.
19. A learning change that affects one future branch leaves unaffected accepted
    Evolutions and their gates intact; only affected progression is revised and
    re-gated.
20. Changed needs or constraints return to Requirements Discovery; changed
    solution commitments or Evolution meaning return to their causal owner;
    Evolve never absorbs them as local Map convenience.
21. A split, merge, or identity change supersedes the old Evolution and creates
    new stable IDs; sequence reordering alone preserves stable IDs.
22. When no multiple meaningful Evolutions remain, Evolve returns a typed
    causal route to Formalize or Requirements Discovery and never mutates the
    Project Brief. It removes an unreferenced Map only after Foundations
    confirms no current record or named consumer references it.
23. Map and Evolution record creation, movement, material revision,
    supersession, and cleanup use Foundations; bodies and gates match
    Formalization; no reference chain appears.
24. `map-proposed`, `map-revised`, `map-approved`, `selection-required`,
    `evolution-selected`, `evolution-specified`, `definition-approved`,
    `causal-return`, `blocked`, and `stopped` remain distinct. Causal,
    blocked, and stopped outcomes contain required typed payloads; every native
    decision is preserved.
25. Approval, selection, Definition Approval, supporting reactions, Result
    Gate approval, and Evolution Acceptance grant no planning, implementation,
