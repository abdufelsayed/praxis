# Formalize — Maintainer Contract

## Purpose

Formalize turns enough accepted truth into a complete current specification.
It recommends and obtains a human route choice among standalone Issues,
direct Project-owned Issues, and Evolve; composes the selected child; checks
semantic coverage; preserves causal returns; updates only Project navigation;
and recommends separate Delivery planning before stopping. Formalize is the
outer owner of this composition. Evolve owns progressive strategy and the
selected high-level Evolution; Define Issues owns detailed Issue records and
Issue Approval.

## Invocation, entry, inputs, and exclusions

Formalize is model-invoked so a direct human request or an explicit human
choice can reach it. Behavioral entry is the human choosing Formalization in
ordinary language after accepted Requirements or conversation has made an
honest specification possible. An accepted Evolution Definition may start
Issue definition only when the human explicitly chooses that activity as a
separate act, either in the same message after Definition Approval or in a
later run. Loading the skill, approving Requirements, approving a Map or
Evolution, or hearing a recommendation does not enter Formalize.
Direct Work may bypass it when a durable Project or explicit specification
would not improve judgment or control.

The entry brief contains the explicit outcome; Project Brief and accepted
Requirements when present; current source and system behavior; interpreted
References and retained artifacts; accepted solution context; uncertainty and
change pressure; entry provenance; caller and earliest causal owner; route,
accepted revisions, gates, authority, acceptance boundary, stop; and the exact
persistence/navigation boundary. A standalone route needs only local accepted
truth; a direct Project or Evolve route needs one accepted Project boundary and
Project Outcome. Formalize never guesses a required boundary, accepted truth,
route, owner, child revision, or authority.

Formalize excludes Requirements Discovery, route automation, record duplication,
child-owned record authorship or gates, implementation planning, mutation,
result acceptance, commit, publication, deployment, and automatic progression.
It may inspect source and evidence, compose bounded child/supporting calls, and
update terse navigation in an existing Project Brief under the caller's
authority. A route discussion creates no approval record and has no
Plannotator gate.

## Behavioral contract

Formalize owns this bounded sequence:

1. Confirm the explicit human-selected entry and bind one outcome, accepted
   truth, Project context when present, route context, authority, and stop.
2. Reconstruct the accepted truth and current evidence at the altitude needed
   for specification, keeping fact, accepted meaning, inference, proposal,
   reaction, and uncertainty distinct.
3. Recommend standalone Issues, direct Project Issues, or Evolve from the
   actual work, explain alternatives, and wait for one conversational human
   selection.
4. Compose only the selected child with a complete current brief, preserving
   its exact results, gates, records, limitations, and non-authorizing
   consequence.
5. Use a bounded supporting capability only for its distinct trigger and
   return its evidence, reaction, comprehension, or finding without
   transferring Formalize ownership.
6. Check the complete current translation semantically, route changed truth to
   the earliest causal owner, revise only affected descendants, and repeat
   only affected child gates.
7. Update only terse Project Brief navigation when a durable Project needs
   continuity; keep governing contents in Requirements, Evolutions, and
   Issues.
8. Explain accepted coverage and safe uncertainty, recommend Delivery
   planning, return one complete envelope, and stop.

## Invariants

1. A direct request or explicit human choice is required. No loaded skill,
   approval, silence, recommendation, sequence position, artifact count,
   feature count, technical layer, expected Issue count, or child result
   satisfies entry or selects a route.
2. One run has exactly one explicit outcome, accepted truth basis, active
   caller, earliest causal owner, route context, current authority, acceptance
   boundary, and stop. Missing or contradictory entry returns the exact typed
   blocker or causal owner.
3. A Project is optional. Formalize does not infer, create, merge, or reshape a
   Project because a route appears convenient. A direct Project route names
   one accepted Project Outcome and boundary.
4. Formalize reads current source, interfaces, runtime behavior, References,
   retained artifacts, accepted solution context, uncertainty, and change
   pressure enough to support the specification judgment. Stale filenames,
   technical structure, and expected artifact count are not evidence.
5. Sourced fact, accepted meaning, inference, proposal, reaction, and
   uncertainty remain distinguishable in route reasoning and returns.
6. Standalone Issues are recommended when no durable Project improves
   judgment or continuity; direct Project Issues when one coherent Project
   Outcome needs detailed specification; Evolve only for an accepted Project
   with at least two meaningful coherent advances whose progressive forms and
   learning matter. Counts never decide alone.
7. Route alternatives are explained with actual consequences and the human
   chooses in ordinary language. The route choice is not a Record Gate,
   approval, Issue Approval, Map Approval, or authority grant.
8. Standalone Define Issues receives no Project parent and enough local
   accepted-truth context to stand alone. Direct Project Define Issues receives
   one Project Outcome and its accepted boundary. Evolve receives one accepted
   Project and returns the accepted Map and selected Evolution. An accepted
   Evolution Definition does not compose Define Issues until the human makes
   a separate explicit Issue-definition choice, either in the same message
   after Definition Approval or in a later run.
9. Evolve owns Map and Evolution records and their native gates. Define Issues
   owns Issue boundaries, bodies, and Issue Approval. Formalize owns neither
   child schema, gate implementation, nor child revision mechanics.
   The Evolve composition is ordered: Map Approval, explicit selection of one
   existing Map entry, and Evolution Definition Approval. Map approval never
   selects; Evolution Definition never starts Issue definition. A
   `definition-approved` result returns the exact child envelope with a
   recommendation and pending `issue-definition` choice, then stops — unless
   the same human message both completed Definition Approval and explicitly
   chose Issue definition as a separate act. A later explicit human choice
   starts Define Issues. Pending selection, pending gate,
   one-advance return, and child `no-op` remain exact states.
10. A child result is composed without flattening: accepted revision, exact
    state, native reference or `unavailable`, feedback, partial records,
    evidence, limitations, safe state, and non-authorizing consequence remain
    visible. A child never selects another route, grants authority, or silently
    re-enters Formalize.
11. A child or supporting stop is not an approval, completion, or command
    failure unless its own contract says so. Formalize preserves the distinction
    between human refusal, native denial, dismissal/closure, transport or
    command failure, blocked dependency, partial acceptance, and causal return.
12. Evolve's one-advance return is evidence for Formalize. Formalize explains
    why direct Issues now fit, recommends that route, and waits for a new human
    selection. It never manufactures a second advance or switches by momentum.
13. If direct Issue work reveals several useful coherent advances whose
    learning should shape later work, Formalize returns the evidence and
    recommends discussing Evolve; it never relabels Issues or changes Project
    ownership silently.
14. A changed need, constraint, preference, problem understanding, accepted
    evidence boundary, Project Outcome, or Project boundary returns to
    Requirements Discovery. A changed progressive strategy returns to the Map
    owner. A changed selected high-level working form returns to the affected
    Evolution. A changed behavior, exclusion, dependency, or proof returns to
    the affected Issue. Formalize does not patch a descendant around a false
    premise.
15. Material revision foregrounds the complete semantic difference, preserves
   still-valid accepted truth, returns affected authority to its pending
   state, and repeats only affected child gates. Its causal return carries
   changed meaning, decisive evidence and limits, affected records and gates,
   safe current state, and a revisit condition. Editorial or provenance-only
   refinement does not become a semantic route change.
16. Coverage is semantic. Complete coverage requires coherent ownership of
    behavior, boundaries, exclusions, dependencies, failure behavior, and
    proof; a mention-count or Requirement-to-Issue ledger is not proof.
17. Change pressure is translated at the correct altitude into ownership,
    interfaces, deliberate limitations, learning targets, and required proof.
    Formalize does not prescribe implementation files, refactoring, commands,
    execution order, or speculative future behavior.
18. Supporting calls are bounded and constructible. Each is composed and
    consumed under caller-local direct-call rules — a complete current brief, a lossless return, no authority
    transfer, and no assurance-path or peer-edge re-entry — and each callee
    owns its intake contract. Research and Interview calls carry the round's
    identity fields (`boundary_id`, `origin=formalize`,
    `return_to=formalize`); Security calls carry the current assurance path.
    A supporting result is evidence, reaction, comprehension, or a bounded
    finding only; it never selects the Formalize route, revises records,
    passes a gate, or continues the loop.
19. Research handles one factual or feasibility premise; Interview handles one
    human-owned judgment; Design Solution handles one complete consequential
    comparison preflight; Make Tangible handles a real fidelity problem;
    Security handles one attacker-focused specification question. Orient is
    human-selected supporting work after an accepted suggestion. Each retains
    its own local ownership and exact return states.
20. Every child and supporting result is retained in one lossless
    `dependency_projections` collection with its exact envelope and a typed
    Formalize mapping. Evolve, Define Issues, Research, Security, Interview,
    Design Solution, Orient, and Make Tangible outcomes map deterministically
    to a pending gate/choice, `formalized`, `partial`, `causal-return`,
    `blocked`, or `stopped`; no native decision, feedback, evidence, limit,
    record, or safe state is flattened.
21. When supporting or child evidence changes earlier governing truth, the
    smallest useful message goes to the earliest causal owner. Learning does
    not become a new phase, backlog, authority source, or duplicate ledger.
    Return handling follows the terminal [Learning and Return](../../references/learning-return.md)
    contract.
22. Formalize creates no `formalization.md`, route decision record,
    orchestration record, duplicate specification, Issue Set, or Formalization
    gate. The selected child invokes its own native gate and owns its current
    records.
23. Project navigation is the only durable write Formalize may own. When a
    Project Brief already exists and continuity needs it, Formalize may update
    terse route, selected Evolution or direct Outcome, governing record links,
    consequential uncertainty, and recommendation. It does not copy record
    bodies or create a Project solely for navigation.
24. A standalone Issue carries enough local context to remain understandable
    without a Project Brief. Evolution and Issue contents remain in their
    owner-shaped records.
25. Formalize is complete only for one of: a complete accepted standalone
    Issue set; complete accepted direct Project-owned Issues; or an accepted
    Map, explicitly human-selected and accepted Evolution Definition, and
    complete accepted Issues for that Evolution.
26. Formalize recommends Delivery planning only after complete current
    specification. Recommendation, child approval, or navigation update grants
    no planning, implementation, mutation, result acceptance, commit,
    publication, deployment, or forward authority.
27. Every outcome carries the caller's retained route, governing records,
    authority, acceptance boundary, and stop, and then stops without adjacent
    work.

## Outcomes and observable return

Formalize exposes exactly these top-level outcomes:

- `formalized` — the selected route's complete current specification is
  accepted by its owning child gates;
- `partial` — some child records or batches are accepted, but required
  coverage or a child gate remains pending;
- `selection-required` — a route was recommended but the human has not made a
  distinct choice;
- `causal-return` — accepted meaning changed and the exact earliest owner,
  semantic difference, safe state, and revisit gate are named;
- `blocked` — missing truth, evidence, authority, dependency, or native
  capability prevents an honest specification; or
- `stopped` — the human or dependency stopped, denied, dismissed, closed, or
  refused the bounded work, with no approval or completion claim.

The semantic envelope is:

```text
Formalize Result {
  outcome: formalized | partial | selection-required | causal-return | blocked | stopped,
  entry_and_human_choice,
  selected_route_and_recommendation,
  pending_human_choice_or_gate?,
  governing_truth_and_accepted_revisions,
  project_navigation_update?,
  records {
    project_brief?,
    map?,
    selected_evolution?,
    issues?,
    child_results
  },
  dependency_projections[] {
    callee,
    exact_child_result,
    formalize_outcome,
    pending_gate_or_choice?,
    causal_return?,
    blocked_state?,
    stop_reason?
  },
  semantic_coverage_and_gaps,
  evidence_and_limits,
  causal_return? {
    earliest_owner,
    changed_meaning,
    affected_records_and_gates,
    safe_state,
    revisit_condition
  },
  stop_reason? {
    kind,
    exact_decision_or_dependency_result,
    native_reference_or_unavailable,
    safe_state,
    limits
  },
  recommendation?,
  caller_retained_route_gate_authority_acceptance_and_stop
}
```

`selection-required` has no selected child or forward activity. `partial`
preserves the exact accepted and pending child state; this includes an
Evolve `definition-approved` result with `pending_human_choice=issue-definition`
and a recommendation for the later choice. `causal-return` has no local repair
claim. `blocked` names the exact missing boundary or native failure. `stopped`
preserves the exact stop and safe state. `formalized` leads with the accepted
records and semantic coverage, names safe uncertainty, and recommends separate
Delivery planning. Supporting evidence or reaction never becomes
`formalized` by itself.

## Effects, authority, persistence, and lifetime

Formalize may inspect current source and evidence, compose listed supporting
skills, and revise current owner-shaped child records only through the child
that owns them. It may update existing Project Brief navigation under current
authority. It does not mutate product code, create Plans, execute work, grant
authority, accept a result, commit, publish, deploy, or make consequential
external changes.

Persist only accepted governing records and the Project navigation that a
named future loop needs. Conversation, route discussion, child messages,
native transport, draft copies, and execution narration are transient by
default. Do not create a Formalization record, route ledger, Issue Set,
message directory, trajectory log, or duplicate learning history. Load the
terminal record references only at their named decision points; do not follow
reference chains.

## Composition and direct calls

Direct calls carry the callee's required brief and preserve its exact return:
 one complete brief, lossless returns, no authority transfer, and no
re-entry of a capability already in the assurance path or across the
Research–Interview edge. Each callee's own contract owns its intake fields.
Research and Interview calls carry the round's identity fields
(`boundary_id`, `origin=formalize`, `return_to=formalize`); Security calls
carry the current assurance path. This package's caller policies are:

| Direct target | Caller policy |
| --- | --- |
| [Evolve](../evolve/SPEC.md) | Human-selected for one accepted Project. Map/Evolution records, gates, and pending states stay exact; `definition-approved` returns with a pending `issue-definition` choice and stops — unless the same human message explicitly chose Issue definition as a separate act; `one-advance` is evidence for a new direct-Issues recommendation, never a route switch. |
| [Define Issues](../define-issues/SPEC.md) | Called only for the explicitly selected route: standalone with no Project parent, direct Project with one accepted Project Outcome and boundary, or a later explicit Issue-definition choice for an accepted Evolution Definition. Only `defined`/`no-op` closes the selected route as `formalized`; a causal `revised` returns to its earliest owner; a non-causal `revised` stays `partial`. |
| [Design Solution](../design-solution/SPEC.md) | `recommended`/`selected`/`qualified`/`no-choice` are usable, non-authorizing comparison input; `refused` blocks the affected choice; `revised` returns to its causal owner. Formalize never guesses a preflight or chooses the result. |
| [Research](../research/SPEC.md) | `answered`/bounded `no-op` are evidence with provenance and limits, never formalization by themselves; `unverified`/`conflicting` leave the claim open, or block when the child declares specification impossible; `revised`/`needs-human-judgment` return to the named owner. |
| [Interview](../interview/SPEC.md) | `clarified`/`qualified`/`no-op` are judgment input; `deferred`/`conflicting` stay pending and are never inferred; `needs-evidence` returns to the exact owner. Changed needs, preferences, Requirements, or Project boundaries map to Requirements Discovery; changed progressive strategy or high-level form maps to the affected Evolution owner. |
| [Orient](../orient/SPEC.md) | Human-selected only after an accepted suggestion. Comprehension is evidence, never a specification decision, approval, or route selection; a changed governing question returns to its owner. |
| [Make Tangible](../make-tangible/SPEC.md) | A constructed or revised artifact with its reaction is usable input within its fidelity, transport, and retention limits; `blocked`/`stopped` stay exact and no reaction is inferred. |
| [Security](../security/SPEC.md) | Integrate only evidence-backed `findings`, `no-high-confidence-findings`, or a scoped `no-op`; `needs-verification` leaves the proof boundary pending; `needs-owner` returns the changed meaning to its governing owner. No finding is a guarantee or remediation. |

Formalize retains route, coverage, causal returns, navigation, and stopping
on every call; no child or supporting result selects another route, grants
authority, or silently re-enters Formalize. Formalize does not call
Plannotator directly. Evolve and Define Issues retain their native Record
Gates; Formalize never substitutes a conversational approval for a selected
native gate.

### Lossless dependency projection

Every direct child or supporting return is stored once in
`dependency_projections[]` with its exact outcome, decisive evidence and
limits, and any caller-needed native reference, record, feedback, partial
state, or safe state, plus the deterministic Formalize projection below. Do
not transcribe generic envelopes or execution history. A `partial` projection
stops this bounded run with the named pending gate, choice, evidence, or
reaction.

| Exact child result | Formalize outcome and pending state |
| --- | --- |
| Evolve `map-proposed`, `map-revised` | `partial`, pending `map-approval`. |
| Evolve `map-approved`, `selection-required` | `partial`, pending explicit `evolution-selection`. |
| Evolve `evolution-selected` | `partial`, pending selected Evolution definition. |
| Evolve `evolution-specified` | `partial`, pending `evolution-definition-approval`. |
| Evolve `definition-approved` | `partial`, pending explicit `issue-definition` choice; return exact child and recommendation, then stop — unless the same human message explicitly chose Issue definition as a separate act. |
| Evolve `one-advance` | `causal-return` to Formalize for a new direct-Issues choice. |
| Evolve `causal-return`, `blocked`, `stopped` | Same typed Formalize outcome, preserving exact payload. |
| Define Issues `defined`, `no-op` | `formalized` only for the already selected route; no new work. |
| Define Issues `partial`, non-causal `revised` | `partial`, pending Issue coverage or affected approval batch. |
| Define Issues causal `revised`, `blocked`, `stopped` | Exact `causal-return`, `blocked`, or `stopped` payload. |
| Research `answered`, `no-op` | `partial`, evidence-ready; no completion claim. |
| Research `unverified`, `conflicting` | `partial`, pending evidence boundary, or `blocked` when the child declares specification impossible. |
| Research `revised`, `needs-human-judgment`, `blocked`, `stopped` | Exact `causal-return`, `blocked`, or `stopped` payload. |
| Security `no-op`, `findings`, `no-high-confidence-findings` | `partial`, evidence-ready with confidence/severity/coverage limits. |
| Security `needs-verification` | `partial`, pending named proof boundary. |
| Security `needs-owner`, `blocked`, `stopped` | Exact `causal-return`, `blocked`, or `stopped` payload. |
| Interview `clarified`, `qualified`, `no-op` | `partial`, judgment-ready. |
| Interview `deferred`, `conflicting` | `partial`, pending human judgment. |
| Interview `needs-evidence`, `blocked`, `stopped` | Exact `causal-return`, `blocked`, or `stopped` payload. |
| Design Solution `recommended`, `selected`, `qualified`, `no-choice` | `partial`, comparison-ready and non-authorizing. |
| Design Solution `revised`, `refused`, `stopped` | Exact `causal-return`, `blocked`, or `stopped` payload (`refused` is a missing/invalid comparison basis). |
| Orient comprehension `explained`, `understanding-observed`, `misconception-unresolved`, `understanding-unconfirmed` | `partial`, comprehension evidence only. |
| Orient comprehension `orientation-blocked` | `blocked`, exact missing/unreliable model or evidence. |
| Orient `causal-return`, `stopped` | Exact `causal-return` or `stopped` payload. |
| Make Tangible `no-op`, `constructed`, `revised` | `partial`, exact surface/reaction ready. |
| Make Tangible `blocked`, `stopped` | Exact `blocked` or `stopped` payload. |

The projection table is exhaustive for the declared direct dependencies. Only
Define Issues `defined`/`no-op` can close an already selected route as
`formalized`; supporting evidence never advances Formalize automatically.

## Package-specific conformance cases

1. **Entry:** a direct human choice of Formalize enters; an accepted
   Requirement, Map, Evolution, recommendation, or loaded skill alone does
   not. An accepted Evolution Definition still requires a new explicit human
   Issue-definition choice before Define Issues is called. Direct Work may
   explicitly bypass when specification would add no control.
2. **Insufficient truth:** missing accepted outcome, governing source,
   evidence, or authority always blocks; a Project boundary is required only
   for direct Project/Evolve routes, while standalone local truth remains
   valid. No child work or record creation begins before the required boundary
   is present.
3. **Route recommendation:** recommendation explains actual outcome,
   complexity, dependencies, current shape, uncertainty, learning value, and
   route consequences; count and technical shape never decide alone.
4. **Human selection:** standalone Issues, direct Project Issues, and Evolve
   are distinct conversational choices. Silence, approval, “continue,” or a
   sequence position produces `selection-required`.
5. **Evolve premise:** Evolve requires a Project and at least two meaningful
   advances. A one-advance return is evidence for direct Issues and waits for
   a new selection; no artificial advance is created.
6. **Direct Issue premise:** evidence of several useful coherent advances is
   returned with a recommendation to discuss Evolve, never silently relabeled.
7. **Child composition:** Evolve and Define Issues retain their records,
   schema, gates, references, feedback, partial state, native decisions, and
   limits; Formalize retains outer route and coverage and creates no duplicate
   gate or record. After Evolve `definition-approved`, Formalize returns the
   exact child result with a pending Issue-definition choice and stops; a later
   explicit choice — or one explicitly stated as a separate act in the same
   human message — calls Define Issues.
8. **Supporting calls:** each call is composed and consumed under caller-local rules below; the callee
   owns its intake contract and a missing required field blocks before
   invocation. Orient requires an accepted human suggestion; comprehension,
   reaction, evidence, or a security finding never becomes approval or route
   selection.
9. **Projection:** every exact Evolve, Define Issues, Research, Security,
   Interview, Design Solution, Orient, and Make Tangible outcome appears once
   in a lossless dependency projection and maps deterministically to a pending
   gate/choice, `formalized`, `partial`, `causal-return`, `blocked`, or
   `stopped` state; no child payload is flattened.
10. **Causal return:** a changed Requirement, preference, Project Outcome, or
   Project boundary returns to Requirements Discovery; progressive strategy to
   Map; high-level form to Evolution; detailed behavior, exclusion,
   dependency, or proof to Issue. Only affected descendants and gates repeat.
11. **Coverage:** complete translation detects conflicting ownership,
    omitted exclusions/dependencies, incompatible failure behavior, and proof
    gaps; it does not rely on mention count or a synthetic ledger.
12. **Navigation:** only an existing Project Brief's terse Current Position,
    route links, uncertainty, and recommendation may be updated. No
    `formalization.md`, route record, or duplicate body is created.
13. **Completion:** the exact complete route is accepted before Delivery is
    recommended; recommendation does not create a Plan, grant authority, or
    advance work.
14. **Stopping:** every result preserves exact route, accepted records,
    references, feedback, safe state, evidence, limits, authority, and stop;
    no adjacent work begins.
