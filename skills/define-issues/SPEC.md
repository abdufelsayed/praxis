# Define Issues — Maintainer Contract

## Purpose

Define Issues translates one accepted high-level outcome into a complete set
of detailed specifications that Delivery can later plan and implement. It
owns collaborative Issue boundaries, reader-ready behavior, coverage,
stable persistence, bounded reaction, Issue Approval presentation, and the
return. It does not own Requirements, Project or Evolution meaning, solution
implementation, planning, authority, or result acceptance.

## Invocation, entry, and exclusions

Define Issues is model-invoked because an active Formalization owner may reach
it after a human chooses detailed specification, and a human may directly
request the same bounded capability. Its behavioral entry is narrower than
host availability: one of the following must be explicit in the current
context:

- a selected Evolution whose complete high-level specification passed
  Evolution Definition Approval;
- a coherent Project Outcome that the human chose to formalize directly as
  Issues; or
- an explicit standalone outcome whose detailed meaning needs judgment.

Approval of Requirements, an Evolution Map, or an Evolution alone does not
invoke Define Issues. Model selection never satisfies a human-owned forward
choice. The entry brief contains the accepted owner and revision, outcome,
governing Requirements or specification, current source, relevant References,
retained artifacts, and human starting point. Exact authority for working
Issue records and any selected native interaction is required when revision or
presentation is needed; a complete accepted set may return early `no-op`
without it.

Define Issues excludes Requirements Discovery, Project or Evolution boundary
selection, high-level Evolution definition, solution implementation, Plan
creation, mutation, acceptance, publication, deployment, automatic
progression, and duplicate Issue Set or Decision records. It does not split
Issues by technical layer, repository, component, file, implementation step,
or expected Plan count unless that split also divides independently judgeable
specification meaning.

## Behavioral contract

Define Issues owns this bounded sequence:

1. Confirm human-selected entry and bind one accepted outcome and revision;
   return an early `no-op` when the complete current accepted Issue set already
   covers that outcome at the same revision.
2. Read current governing context and close bounded factual, human, context,
   perceptual, or solution gaps without taking earlier-owner meaning.
3. Propose and discuss Issue boundaries based on independently judgeable
   specification meaning.
4. Write each Issue as a reader-ready current specification with observable
   requirements, boundaries, exclusions, dependencies, and proof.
5. Check complete outcome coverage and return any changed earlier meaning to
   its causal owner.
6. Persist only stable owner-shaped Issue records when a named future loop or
   gate needs them.
7. Optionally collect grounded facts reactions and present complete Issue
   sets through bounded native or conversational Issue Approval batches.
8. Revise affected Issues and repeat only affected approval batches when
   accepted meaning changes; return complete coverage, recommendation, and
   stop.

## Invariants

1. One run has exactly one explicit entry owner, accepted revision, selected
   outcome, and current route, or returns a precise `blocked`/`stopped` state.
2. Define Issues begins only after a human chooses detailed specification for
   an accepted Evolution, direct Project Outcome, or standalone outcome; no
   approval or loaded skill starts it automatically.
3. Requirements, accepted solution context, current source, References, and
   retained artifacts are read at the depth needed for honest Issue meaning;
   sourced fact, accepted truth, inference, proposal, reaction, and
   uncertainty remain distinct.
4. One Issue remains coherent when behavior, exclusions, dependencies, and
   proof can be understood and judged together; sibling Issues split only
   independently judgeable specification meaning.
5. Frontend/backend, repository, component, technical layer, implementation
   step, command, file, and expected Plan boundaries are not Issue boundaries
   without an independent observable meaning boundary.
6. Every Issue has one concise observable outcome, enough Context for an
   independent reader, complete governing Requirements, meaningful exclusions
   and dependencies when applicable, and observable Acceptance Criteria.
7. Acceptance Criteria state claims and boundaries, not test files, commands,
   frameworks, code seams, execution order, or task checklists. Illustrative
   examples remain non-exhaustive unless explicitly declared exhaustive.
8. Inherited accepted behavior materially exposed through a shared invariant,
   interface, responsibility, or known pressure point appears in affected
   Acceptance Criteria; Formalization does not ritualistically repeat
   unrelated Project checks.
9. Implementation mechanics remain with Delivery Plans. Issues do not become
   task logs, command ledgers, Plan histories, or result archives.
10. The complete Issue set covers every material behavior, constraint,
    exclusion, dependency/order relationship, and required proof of the
    selected outcome, or names the exact causal owner and gap.
11. Before drafting or re-gating, an already complete accepted Issue set at the
    current entry revision returns `no-op` with its selected outcome and
    governing truth, exact IDs, paths, accepted batches, references, evidence,
    and limits; no ceremony reopens it. If a
    supporting result changes a Requirement, Project boundary, preference,
    problem understanding, progressive strategy, or high-level working form,
    Define Issues returns it to that earliest owner and does not patch a
    descendant Issue.
12. Research is called only for one bounded discoverable fact; Interview only
    for one human-owned specification judgment; Orient only after accepted
    human consent for one settled context model; Make Tangible only for a
    material perceptual/fidelity gap; Design Solution only for one complete
    consequential choice preflight; and Plannotator only for its selected
    native facts or Issue Approval interaction.
13. Each direct call carries one precise trigger, bounded brief, expected
    result, and caller-retained ownership. No callee transfers authority,
    chooses a route, approves an Issue, or silently re-enters Define Issues.
14. Research returns preserve evidence status and limits; Interview preserves
    qualified, deferred, conflicting, and stopped human meaning, while Define
    Issues maps a preference or Requirement change to `revised` at its
    earliest owner;
    Orient preserves comprehension, causal-return, and stopped states; Make
    Tangible preserves exact artifact/version, reaction, fidelity, lifecycle,
    blocked, and stopped state; Design Solution preserves every top-level
    design outcome; and Plannotator preserves approval, feedback, dismissal,
    denial, closure, and transport failure distinctly.
15. Durable Issue files are owner-shaped, lowercase, stable, unique across
    `.agents/`, and use the common envelope and Formalization Issue body.
    Moving an accepted record changes no authority; refinement keeps its ID;
    splitting, merging, or replacing creates new IDs with minimal
    supersession context.
16. A standalone Issue omits `parent` and carries enough Context to stand
    alone. An Evolution- or Project-owned Issue names the nearest governing
    parent. No empty optional directory, placeholder, generic template, or
    duplicate collection record is created.
17. An Issue remains a current specification. After accepted Delivery affects
    it, one concise current Result summary records proved coverage, decisive
    evidence pointers, and remaining unmet criteria or limitations; execution
    history stays outside it.
18. Optional facts reaction edits only the exact current Issue content and
    creates no Fact or Issue Set record. Approved non-blocking Plannotator
    feedback is preserved with its accepted batch and does not reopen it;
    feedback that changes an upstream Requirement or preference, or other
    governing meaning, returns to the earliest causal owner and repeats every
    affected Issue batch.
19. Issue Approval presents complete stable Issue files in one or more bounded
    coherent batches, names exact Issue IDs, keeps cross-batch dependencies
    visible, and creates no duplicate collection. A selected native Record
    Gate is authoritative; when no native surface is selected, an equivalent
    conversational approval captures the same complete target, decision, and
    feedback and projects `accepted_reference: unavailable` when accepted.
    Approval accepts only the named specifications and grants no planning,
    mutation, commit, publication, deployment, or route authority.
20. Dismissal, native denial, empty closure, native failure, missing authority,
    missing dependency, and human stop remain distinct from approval and from
    one another wherever the returned surface exposes them. Native denial maps
    to `stopped` with its exact decision, reference or `unavailable`,
    fidelity/transport limits, and preserved safe state; a selected native
    surface is never replaced by conversational approval.
21. Approval of a complete set leads only to a recommendation for Delivery
    planning and a stop. Define Issues never creates a Plan, implements,
    accepts a result, commits, publishes, deploys, or advances another route.
22. Every return identifies exact Issue identities and paths, the selected
    outcome and governing truth, complete or partial coverage, accepted and
    pending batches, native references and revision scope, decisive evidence
    and limitations, unresolved obligations or causal return, caller-retained
    controls, and the human judgment still needed.

## Outcomes and observable return

Define Issues exposes:

- `defined` — every Issue required for the current outcome is reader-ready and
  its Issue Approval is accepted;
- `partial` — named batches or Issue coverage are accepted but required
  outcome coverage or approval remains pending;
- `no-op` — an already complete accepted Issue set needs no ceremonial rewrite
  or second gate;
- `revised` — a material semantic or ownership change invalidates affected
  Issue meaning or approval and requires a new bounded revision;
- `blocked` — missing entry, evidence, authority, dependency, native
  capability, or honest coverage prevents progress; or
- `stopped` — the human declined, dismissed, denied, or stopped the bounded
  work, preserving current safe state without inferred acceptance. A native
  denial keeps its exact decision, reference or `unavailable`, and
  fidelity/transport limits.

The semantic return is:

```text
Define Issues Result {
  outcome: defined | partial | no-op | revised | blocked | stopped,
  entry_owner_and_revision,
  selected_outcome_and_governing_truth,
  issue_ids_and_owner_paths,
  boundaries_and_coverage,
  accepted_and_pending_issue_batches,
  native_references_and_revision_scope,
  evidence_and_limits,
  unresolved_or_causal_return,
  recommendation,
  caller_retained_route_gate_authority_acceptance_and_stop
}
```

`defined` leads with the complete set, accepted batches, decisive evidence,
and a Delivery-planning recommendation. `partial` names exactly what was
accepted and what remains; it never implies that unaccepted Issues may be
planned. `no-op` identifies the existing complete set and why no ceremony was
needed. `revised` carries the semantic diff, affected owner or Issues, still
valid evidence, and gate to repeat. `blocked` identifies the precise missing
boundary and any preserved partial records. `stopped` preserves current state,
and for a native denial the exact decision, reference, and fidelity/transport
limits; it makes no comprehension, approval, authority, or acceptance claim.
Every result states that the caller retains governing meaning, route, gates,
authority, acceptance, and stopping.

## Effects, authority, persistence, and lifetime

Define Issues may inspect current source and evidence, revise working Issue
files inside the caller's existing authority, and invoke the selected bounded
supporting capabilities. It does not mutate product code, execute a Delivery
Plan, publish, commit, deploy, accept a result, or create a route transition.
Native Plannotator approval is a human judgment over exact Issue files, not
planning or Implementation Authorization.

Durable Issue records are created only when a named future owner or gate needs
their governing meaning, work must survive the conversation, or the human
explicitly asks for persistence. Conversation, temporary facts transport,
reaction, and discarded drafts remain transient. The only durable Issue
locations are `.agents/projects/<project>/issues/` and `.agents/issues/`.
Exact native gate references may be projected into the Issue envelope; when no
reliable native reference exists, use `accepted_reference: unavailable` and
present the complete current target later. Define Issues creates no Issue Set,
Fact, transcript, approval history, Plan, or generic learning ledger.

An accepted semantic revision returns to the earliest causal owner, repeats
the affected Issue Approval batches, and invalidates dependent planning
authority according to the caller's control rules. Unaffected Issues retain
their accepted meaning when their shared interfaces, invariants, dependencies,
and proof remain valid.

## Package-specific conformance cases

1. **Three entry owners:** an accepted Evolution after Definition Approval,
   a direct Project Outcome, and a standalone outcome each enter only after a
   human choice; an accepted Requirement, Map, or Evolution alone does not.
2. **Premature entry:** a loaded or implicitly selected package returns
   `blocked`/`stopped` without drafting when the human has not chosen Issue
   definition or the accepted owner/revision is missing. An already complete
   accepted set at the current revision returns `no-op` before drafting or
   re-gating, with its exact IDs, paths, batches, references, evidence, and
   limits.
3. **Collaborative boundaries:** one coherent behavior stays one Issue;
   independently judgeable outcomes split; frontend/backend, repository,
   component, or Plan boundaries do not split meaning by themselves.
4. **Reader-ready Issue:** each file has the exact stable envelope, observable
   outcome, Context, complete Requirements, meaningful optional sections, and
   Acceptance Criteria that a future engineer can judge without workflow
   narration.
5. **Complete coverage gap:** every material behavior, constraint, exclusion,
   dependency, and proof is owned, or the exact gap and causal owner returns;
   no traceability ledger is manufactured.
6. **Implementation detail:** files, commands, code structure, tests, order,
   and mutation authority remain for Delivery planning rather than entering
   an Issue's specification.
7. **Research:** one factual question carries stable boundary and peer fields;
   answered, unverified, conflicting, revised, no-op, needs-human-judgment,
   blocked, and stopped returns remain distinct and never invent evidence.
8. **Interview:** one human-owned choice preserves clarified, qualified,
   deferred, conflicting, no-op, needs-evidence, blocked, and stopped meaning;
   a changed preference or Requirement is `revised` to the earliest owner and
   is not absorbed into an Issue.
9. **Orient:** teaching starts only after accepted human suggestion or direct
   request, and comprehension is not approval; causal returns preserve the
   exact earlier owner or affected Issue.
10. **Make Tangible:** a flow/state/interface surface is used only when prose
    cannot support judgment; exact artifact/version, reaction, fidelity,
    retention, blocked, and stopped states survive without an inferred Issue
    acceptance.
11. **Design Solution:** a consequential complete preflight produces a
    bounded recommendation, selection, qualified, no-choice, revised,
    refused, or stopped return without choosing implementation or route.
12. **Optional facts reaction:** the native `Bundled facts` interaction
    round-trips stable IDs and every edit, comment, removal, accepted state,
    and verification choice; no Fact or Issue Set record is created; a meaning
    change reopens affected Issues.
13. **Issue Approval:** native Record Gate batches are authoritative when
    selected; otherwise an equivalent conversational approval presents the
    same complete files and exact IDs. Both preserve cross-batch dependencies,
    capture the exact decision and feedback, keep approved non-blocking
    feedback without re-gating, re-gate only meaning-changing feedback,
    accept only named specifications, and create no duplicate collection
    record.
14. **Approval stopping:** approval grants no planning, mutation, commit,
    publication, deployment, or next route; after complete coverage the
    result recommends Delivery planning and stops.
15. **Cross-batch dependency:** a later batch sees its semantic dependency on
    an earlier batch; pending or rejected batches remain unaccepted and block
    dependent planning.
16. **Shared semantic revision:** a changed shared interface, invariant,
    dependency, or proof updates every affected Issue and repeats each
    affected batch; unaffected Issues retain accepted meaning.
17. **Stable IDs:** refinement or ownership move preserves an ID; split,
    merge, or replacement creates new IDs with minimal supersession context.
18. **Partial accepted coverage:** accepted batches return `partial` with
    exact accepted and pending coverage and no planning claim for pending
    Issues.
19. **Native failure and denial:** Plannotator denial maps to `stopped` with
    its exact decision, native reference or `unavailable`, fidelity/transport
    limits, and preserved safe state; dismissal or empty closure is also
    `stopped`, while malformed result or transport failure is `blocked`. A
    selected native gate never falls back to conversational approval.
20. **Persistence:** durable files appear only at owner-shaped paths; drafts,
    facts transport, reaction, and execution history remain transient unless
    a named consumer needs them.
