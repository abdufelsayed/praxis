# Capability catalog

This is a lookup catalog, not a lifecycle or automatic route. One active
Inquiry is the unit of work. Capabilities have different roles inside it:

- **Lifecycle:** Using Praxis, Discover Requirements, Formalize, Evolve,
  Define Issues, Plan, Deliver, and Coordinate Initiative help establish or
  change the Inquiry's working position and durable governing form.
- **Supporting:** Research, Interview, Design Solution, Make Tangible, Orient,
  Debug, Refactor, TDD, Review, Security, Verify, and Delegate answer bounded
  questions or produce bounded evidence without taking lifecycle control.
- **Interaction and effect control:** Plannotator, Check Safety, and Pair carry
  a selected interaction, preflight, or collaboration posture.
- **Repository and communication:** Manage Worktree, Setup, Commit, Prepare PR,
  and Write Docs perform explicit repository or durable communication work.

These roles are not peers in a hidden router. A direct request may establish a
bounded Inquiry and load the smallest useful capability without requiring the
requester to know its name. [Integration status](integrations.md) is the
availability and support-boundary authority.

Each entry gives three things: what the capability owns, how its behavior may
begin, and the bounded result it returns. Executable procedures belong to
runtime; maintainer behavioral contracts are never agent context.

## Understanding and requirements

### Discover Requirements

Helps expose consequential unknown needs, constraints, assumptions, feasibility,
preferences, and blind spots until the next governing judgment is honest.
Begins when such uncertainty blocks an honest route, specification, or
contained edit; clear work skips it. Returns synthesized Requirements truth,
evidence, reactions, safe-to-carry uncertainty, and an alignment or honest
non-convergence state to the exact owner. Substantial research is harvested
through concrete paired judgments before it can support atomic Requirements.
A transition brief and provisional topic map separate factual visibility from
requester-selected product judgment.

### Research

Answers one bounded discoverable factual question using current code, primary
external evidence, history, or an empirical probe. Begins from an explicit
factual gap or a caller’s bounded factual need; routine task-local inspection
stays with its owner. Returns answered, sufficient-existing-context (`no-op`),
unverified, conflicting, revised, needs-human-judgment, blocked, or stopped
state with scope, decisive evidence, limitations, and implications.
Substantial work automatically updates one canonical Research Findings record
for its named consumer when the Inquiry's persistence policy permits it; that
record remains evidence rather than product truth.

### Interview

Resolves one human-owned intent, preference, priority, tolerance, or
recognition-based judgment. Begins when source evidence cannot determine that
choice, or from a direct request for that bounded conversation; discoverable
facts stay with Research. Returns the scoped answer, consequences, deferred
uncertainty, and a recommendation only when supported. Dependent judgments
stay adaptive in conversation; independent grounded judgments may use one
Plannotator bundle.

### Make Tangible

Constructs the smallest faithful artifact, prototype, visualization,
simulation, comparison, or teaching/reaction surface that makes a caller-owned
judgment easier. Begins when words impose material judgment cost and a
perceptible surface can reduce it. Returns the exact artifact or surface,
judged version, reaction, supported conclusions, fidelity, and lifetime limits;
the caller retains meaning and gates.

### Orient

Teaches one settled mental model for comprehension. Begins after a direct
request from the requester or an accepted bounded orientation suggestion; it does not begin
automatically. Returns the model taught, comprehension state, remaining
uncertainty, and any consequential discovery to its causal owner.

## Formalization

### Formalize

Determines whether accepted truth is ready and makes the specification working
forms judgeable: standalone Issues, direct Project Issues, or Evolve. Begins
when the requester selects shaping sufficient accepted truth; no capability
name is required and Requirements Alignment alone does not invoke it. Transfers
complete governing context to the selected form and stops; it does not remain
a hidden parent or own child gates.

### Evolve

Designs a Project-specific progression of at least two independently meaningful
working forms, then develops the Evolution selected by the requester’s
high-level specification. Begins after the requester chooses Evolve following a route
recommendation. Returns an accepted or revised Evolution Map, the selected
Evolution definition when chosen, learning targets, limitations, and the next
human-owned gate; Map Approval selects nothing by itself.

### Define Issues

Turns one accepted Evolution, direct Project Outcome, or standalone outcome
into detailed, reader-ready Issues describing observable truth and proof.
Begins only after the requester chooses Issue definition for one of those owners.
Returns a complete judgeable Issue set or an explicit coverage gap, plus the
exact approved batch and its limitations; approval grants no planning authority.

### Design Solution

Makes one consequential solution shape judgeable across behavior, ownership,
contracts, operations, migration, security, or reversibility. Begins when
accepted Requirements allow materially different shapes, from a caller or a
direct bounded request. Returns `recommended`, `selected`, `qualified`,
`no-choice`, changed-meaning, blocked, or stopped state with rationale,
consequences, evidence, uncertainty, and causal owner. Recommendation is not
human selection, and selection grants no implementation authority.

## Delivery and assurance

### Deliver

Owns one bounded integrated implementation result, coordination, assurance,
Result Acceptance, learning, and stop. Clear reversible work may enter without
a Plan when target, exclusions, risk, authority, and proof are already settled;
otherwise it begins after separate authorization of an approved Plan. Returns
the exact proved and unproved coverage, evidence, limits, learning, and current
authority state. Acceptance exhausts authority for its exact boundary and
starts nothing else.

### Plan

Defines one judgeable Implementation Plan: approach, targets, authority,
exclusions, risks, recovery, integration, and proof. Begins from a direct
planning request or after the requester chooses planning inside Delivery. Returns a
complete provisionally approved or revised Plan and its authority boundary;
Plan Approval never authorizes implementation.

### Debug

Diagnoses one failing, intermittent, or unexpectedly slow behavior when its
cause or correct fix is unknown. Begins when that trigger appears in Direct
Work or authorized Delivery; a demonstrated cause stays with the ordinary
owner. Returns a proved cause, bounded correction or blocker, regression and
original-reproduction evidence, cleaned diagnostic state, and causal learning.

### Refactor

Relieves one demonstrated structural pressure while preserving accepted
behavior. Begins when ownership, dependency, compatibility, seam, or
modification friction has a concrete mechanism; size or style preference alone
does not trigger it. Returns the pressure-point transformation, preservation
evidence, limits, and any adjacent work left outside authority.

### TDD

Develops one settled behavior through an honest red–green–refactor cycle.
Begins when the requester requests test-first work or Delivery/Debug has a stable
red-first proving seam. Returns the failing-for-the-right-reason test,
smallest implementation that earns green, preservation evidence, or an honest
return when the claim cannot be proved at that seam.

### Review

Challenges one fixed proposal, record, code target, delivered result, or
external comment for concrete failure mechanisms and quality risks. Begins when
an owner needs adversarial judgment; Deliver invokes it before presenting a
implementation result. Returns complete or explicitly incomplete coverage,
prioritized evidence-backed findings, rejected or unresolved feedback, and
limits—not approval.

### Security

Investigates one bounded attacker-focused question across trust boundaries,
identity, authorization, attacker-controlled input, sensitive data, secrets,
dependencies, remote execution, or deployment exposure. Begins when a credible
attack surface or attacker-focused question appears; direct security review of
a fixed target remains Review-owned and composes this capability. Returns
validated findings, unresolved candidates, separate hardening suggestions,
coverage limits, confidence versus severity, and the exact causal owner; it
does not approve remediation or accept a result.

### Verify

Tests exact completion claims with current falsifiable evidence. Begins before
a material completion claim or when an owner needs bounded proof; it does not
diagnose unknown causes. Returns `verified`, `failed`, or `unverified` status
for each claim with target, evidence, environment, expected/observed result,
and limitations.

### Delegate

Assigns one bounded question or outcome when isolated context, independent
evidence, cost, or elapsed-time benefit outweighs coordination. Begins from a
supervisor decision, never by default. Returns compact evidence, findings or
changes, verification, limitations, deviations, and a recommended next step;
the supervisor retains integration, authority, acceptance, and stopping.

## Interaction and control

### Plannotator

Presents one exact target through a selected native annotation, gate, fixed-diff
review, bundled question, or Review Learning interaction. Begins when an owning
skill selects that native path or the requester directly requests a Plannotator
utility. Returns decision, annotations, reaction, fidelity limits, and a
reliable native reference; approval never becomes implementation authority.

### Check Safety

Preflights one consequential action before execution. Begins for a real
destructive, irreversible, production, data, permission, secret, cross-project,
infrastructure, or comparable effect after Plan coverage and exact authority
are eligible. Returns `proceed`, `revise`, or `stop` scoped to the action and
current state, with evidence and limitations; it never performs the action.

### Using Praxis

Establishes or reconstructs one active Inquiry and loads the smallest useful
capability. Begins when Praxis is explicitly requested, current Praxis context
matters, or the correct working position is genuinely ambiguous. Returns the
Inquiry envelope and transition recommendation; it performs no owner work,
and stores no hidden global state.

### Pair

Provides literal collaborative implementation in decision-sized turns. Begins
only from a direct human request inside an authorized implementation boundary;
it is not inferred or recommended. Returns the integrated result, evidence,
and any partial state to its caller while keeping each mutation permission
scoped and revocable.

## Strategic and repository support

### Coordinate Initiative

Preserves shared strategic meaning across multiple independently governed
Projects. Begins after the requester chooses coordination when at least two
credible Project candidates share an objective, constraint, relationship, or
learning. Returns aligned shared truth, affected Projects, causal learning,
and Initiative Alignment or closure state; it starts no Project.

### Manage Worktree

Manages one Git worktree for a named collision, preservation, rollback,
parallel-editor, or repository-experiment risk. Begins only when that concrete
risk justifies checkout isolation; a dirty tree alone does not. Returns current
checkout safe, worktree ready, handoff ready, cleanup complete, blocked, or
stopped with exact identity and limits.

### Setup

Prepares the smallest repository-local Praxis environment and named native
integration. Begins only from an explicit Setup request for readiness, repair,
Plannotator, a named integration, removal, or Docker for a selected Security
audit. Returns configured and already-correct state, verification, unavailable
capabilities, limits, and one useful recommendation; it starts no audit.

### Commit

Records one intentional coherent local Git snapshot. Begins only from an
explicit request to create, amend, or otherwise operate on a commit. Returns
commit identity, included intention, decisive verification, hooks or approved
exceptions, and remaining work; it does not push, open a PR, merge, deploy, or
continue Delivery.

### Prepare PR

Prepares one reviewer-ready pull or merge request from the exact reviewed
base-to-head change. Begins from an explicit request to prepare, create, or
refresh a PR; a local result never grants publication authority. `prepare` or
`draft` may return a local proposal with no provider effect. Explicit create,
refresh, readiness, reviewer, or metadata requests authorize only those named
effects. A remote result includes its URL, draft state, represented snapshot,
verification, and remaining unpublished state. It pushes only when the requester
separately authorizes the exact unchanged reviewed head, remote, branch, and
effect; consequential publication retains Plan and Safety requirements.

### Write Docs

Creates current-source documentation for one named reader and purpose. Begins
from an explicit documentation request or an authorized implementation boundary
that names a documentation result. Returns the surfaces changed, reader need served,
current-source and reader-journey verification, and material gaps; publication,
release, and adjacent documentation remain separate effects.
